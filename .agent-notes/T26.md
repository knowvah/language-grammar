## Observation: mindmap/WBS tree checks depend on leading blanks the interpreter never sees
- **Context**: classifying the 7 pdiff FAs of the mindmap-wbs slice (all tree structure).
- **Finding**: item levels come from getSmartLevel on the untrimmed marker run (mindmap/MindMapDiagram.java:136-157, wbs/WBSDiagram.java:187-208); CommandMindMapOrgmode/Plus and CommandWBSItemNew/Old use `SingleLineCommand2(doTrim=false)`. In WBS ` * x` under `* root` is level 1 (accepted, pdiff input/WBS-monoline-def-0.puml#1) while `* x` is a second root (rejected), so on trimmed lines every second-root or depth-jump reject would add false rejects. 24 commands at the pin use doTrim=false (board, chart, mindmap, salt CommandAnything, wbs, wire).
- **Impact**: tree checks are gaps (tests/fixtures/mindmap-wbs/gap); raw-line matching was queued in reports/queued-shared-changes.md ("mindmap-wbs: match ... untrimmed line") and landed during T26 as entry key `trim: false` (generated models regenerated); that closed gap/mindmap-indented-plus and gap/wbs-pseudo-trailing-blank (now neg/), but the level checks still need per-level state contexts. Other doTrim=false families have the same blind spot for leading/trailing blanks.
- **Confidence**: High (oracle probes, `-syntax` messages)

## Observation: missing roots are fine; mindmap and WBS differ on later level-0 items and jumps
- **Context**: the task asked whether the jar rejects depth jumps or a missing root.
- **Finding**: the first idea is the root at any depth in both (mindmap/MindMap.java:120-121, wbs/WBSDiagram.java:188-193); a body with no idea at all (`title x`) is accepted. Mindmap: a later level-0 idea starts a new mind map (MindMapDiagram.java:120-121); the first child's level is a per-map multiplier, so `*`/`***`/`*****` is accepted and `*`/`***`/`**` fails "Bad indentation" (MindMap.java:129-135); `*`/`**`/`****` fails "error42L" (Branch.java:87); `+` and `-` sides keep separate last ideas. WBS: a later level-0 item fails "only accepts one root" (:160-162), `*`/`***` fails "Bad tree structure" (:230), no multiplier.
- **Impact**: pos/neg/gap fixtures pin each case.
- **Confidence**: High (oracle-verified)

## Observation: WBS link codes exclude the root; `<_` never matches
- **Context**: WBS link and shape fixtures.
- **Finding**: the root's `(code)` is never stored (WBSDiagram.java:160-165 calls initRoot, codes.put only in add), so `*(a) root` / `**(b) B` / `a -> b` fails "No such node a". The shape/direction RegexOr has three branches `(_)?([<>])?` | `([<>])?` | `(_)?` (wbs/CommandWBSItemNew.java:86-92), so `**<_ x` is a syntax error while `**_< x` works.
- **Confidence**: High (oracle-verified)

## Observation: where a `[#color]` is a color differs between mindmap and WBS
- **Context**: unknown-color rejects.
- **Finding**: mindmap takes `[#...]` as a color only right after a homogeneous marker run (`**[#x]`, `++[#x]`); after `_`, a blank or a mixed run like `*+`, it is label text, and `[#ä]` (Java `\w` is ASCII) is label text too. In WBS a `[#...]` right after markers/shape/`(code)` that is not `#\w+` is a syntax error. Valid words: transparent/background/automatic, hex of 1/3/6/8 digits, the 154 ColorTrieNode names (ASCII case-insensitive); `[#ff]`, `[#ffff]`, `[#red_]` fail.
- **Confidence**: High (oracle-verified)

## Observation: standalone `\b` leaves vanish in Lark
- **Context**: Lark run over the mindmap-wbs fixtures (neg/mindmap-not-a-direction).
- **Finding**: generated CommandMindMapDirection has `\b` as separate regex leaves; the Lark emitter drops zero-width terminals, so Lark accepted `lefty side` (jar and interpreter reject). Folding both `\b` into the DIRECTION leaf (`\b(left|right|top|bottom)\b`, an override in mindmap-wbs-mindmap) keeps the language and makes Lark reject it.
- **Impact**: any generated rule with a standalone `\b`/lookaround leaf is wider in Lark; folding it into a neighbouring non-empty leaf is a cheap family-level fix.
- **Confidence**: High (Lark probes on a scratch build)
