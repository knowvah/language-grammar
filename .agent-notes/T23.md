## Observation: `[\s\_]` in the generated YAML is a no-break space, not an underscore
- **Context**: Deciding whether a head reject for `0 is X` could steal `_5 is x` or `title_*2 is x` from an earlier command.
- **Finding**: In YAML double quotes, `\_` is the escape for U+00A0. The generated `"[\\s\_]+"` is `[\s ]+`, which is upstream `%s` (`regex/Pattern2.java:54-59`). An underscore is never a blank. Two guards I wrote for `_` collisions were therefore wrong and caused false accepts (`iis*2 is x`). The jar confirms that `title_*2 is x` is not a title.
- **Impact**: When reasoning about which command can match a line, read `[\s ]` in compiled patterns as whitespace plus NBSP only.
- **Confidence**: High (oracle-verified)

## Observation: timing state commands need a current player (TimingDiagram.lastPlayer)
- **Context**: Checking which timing state errors the jar reports.
- **Finding**: `0 is X` (CommandChangeStateByTime.java:102-104) and `@0 <-> @5` without a player (CommandConstraint.java:112-115) fail until a robust/concise/rectangle player is created (TimingDiagram.java:291-315) or `@X` names an existing player (CommandAtPlayer.java:79). Clock, binary and analog players do not set the current player. The model encodes this with `set: timing_player` and two head rejects in `main`.
- **Impact**: Other lookups are semantic gaps: undeclared players, time labels and clocks, and players that refuse states (a clock throws UnsupportedOperationException).
- **Confidence**: High (oracle-verified)

## Observation: runtime exceptions in executeArg are execution errors
- **Context**: `scale 1 as 99999999999999999999 pixels`, `@99999999999:0:0`.
- **Finding**: NumberFormatException from Long/Integer.parseInt or new BigDecimal is caught by command/ProtectedCommand.java:65-76 and becomes CommandExecutionResult.error, so the jar rejects. Integer overflow in arithmetic (`3600 * h`, tick times the unit factor) wraps silently instead.
- **Impact**: Any `parseInt`/`parseLong`/`new BigDecimal` on a `\d+` or `[.\d]+` capture is a regex-expressible reject.
- **Confidence**: High

## Observation: generated `\d` is Unicode in the interpreter, ASCII upstream
- **Context**: Writing the reject shapes for time literals.
- **Finding**: Pattern2 compiles without UNICODE_CHARACTER_CLASS, so Java's `\d` is `[0-9]`. Python `regex` matches Unicode digits with `\d`. Generated rules keep `\d`, so they accept, for example, Arabic-Indic digits in times that upstream does not match. The timing hand-written parts use `[0-9]`.
- **Impact**: This is a latent extractor/translator divergence in every generated model. It is harmless only while no corpus uses non-ASCII digits.
- **Confidence**: High (source); Low (corpus impact, not measured)

## Observation: narrowing a trailing time needs a reject before the command
- **Context**: `R@0 -> R@5:0:99999999999` (TimeMessage TIME2), the Constraint TIME2 slot, and `highlight 0 to 5:0:99999999999`.
- **Finding**: Upstream tries HOUR before DIGIT. When the trailing slot is followed by an optional `: text`, a narrowed HOUR lets the regex fall back to DIGIT `5` plus the message `0:99999999999`, so a reject placed after the rule never fires. A reject with an overflowing HOUR placed before the command (insert_before) is exact.
- **Impact**: Any narrowing inside an alternation followed by a free-text tail must check whether a later alternative can absorb the text.
- **Confidence**: High (oracle-verified)

## Observation: Lark rejects a `set` into a pop-less context on the last body line
- **Context**: pdiff `--lark all` showed 3 disagreements (`concise ... as X` / `@X` as the last line).
- **Finding**: The emitter writes `<parts> _NL <ctx>_block`, the body adds its own `_NL`, and the empty context needs a second newline. A monkeypatched emitter with `(_NL line?)*` contexts fixes all 3. The fix is queued in reports/queued-shared-changes.md.
- **Impact**: class (`class_orphan`, `main_mixing`) and description (`desc_orphan`, newpage) set targets have the same shape.
- **Confidence**: High
