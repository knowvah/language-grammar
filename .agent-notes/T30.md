## Observation: a terminal regex whose first match undershoots is a Lark false reject
- **Context**: 29 of 55 pdiff chart blocks rejected by Lark after narrowing the chart value lists.
- **Finding**: Lark's dynamic lexer takes one `regex.match` per terminal and only shortens it. Three shapes made the first match shorter than the intended one while the interpreter's fullmatch backtracked past them: (1) an alternation whose first branch matches empty (`(?:\s*|items)`), (2) a decimal branch before a hex branch (`0` of `0x1p3`), (3) a greedy trailing `)` run that eats the `)` of the next `),(` separator. Reordering (longest branch first, hex first) and a `(?!,\()` guard on the closer fix all three without changing the language (200k-string fuzz against a Java reference). The family test now asserts "no undershoot" for the chart number grammars.
- **Impact**: any hand-written regex used as one emitted terminal must prefer its longest valid match; check with `regex.match(text + following)` rather than fullmatch.
- **Confidence**: High (fuzzed; pdiff Lark 29 -> 0 disagreements)

## Observation: chart data parsing follows Java String.split quirks
- **Context**: modelling `bar [...]`, `line [(x,y),...]`, `v-axis ticks [...]`.
- **Finding**: `split(",")` drops trailing empty strings, so `[1,2,]`, `[,]` and `[),(]` (zero pairs) are accepted while `[,1]`, `[ , ]` and `[1,,2]` fail. Coordinate data has all ASCII whitespace removed first, so `(1 .5,2)` is the pair (1.5, 2). `v-axis [labels]` returns before range/ticks/spacing are parsed, so `v-axis [a] spacing 0` is accepted. Double.parseDouble accepts hex floats, NaN/Infinity (case-sensitive) and f/d suffixes. All oracle-verified.
- **Confidence**: High
